# On-chain erasure attestation

Two contracts that move CHRONOS erasure verification from "trust the operator's
server" to "check the chain".

| Contract | Purpose |
|---|---|
| `Groth16Verifier.sol` | Verifies BN254 Groth16 proofs via the EVM `alt_bn128` precompiles (`0x06`, `0x07`, `0x08`) |
| `ChronosRegistry.sol` | Append-only registry of verified attestations, one per mission |

BN254 is the curve the EVM calls `alt_bn128`, which is why the erasure circuit
targets it — a proof generated by `chronos-snark` is checkable by any Ethereum
node with no additional trust.

## What an accepted proof actually means

Read this before citing on-chain verification as a containment guarantee.

**It proves:** someone knew a witness satisfying the erasure circuit for the
given public inputs, under the deployed verifying key. Concretely, that all 32
bytes of a key buffer held the declared wipe pattern, and that the prover's VDF
output byte matched the claimed one.

**It does not prove the agent was contained.** Three gaps, in order of severity:

1. **The trusted setup is currently single-party.** `mpc_ceremony_rng` XOR-folds
   three RNGs inside one process, so whoever ran setup holds the trapdoor and can
   forge proofs that verify here perfectly. Until a real Powers-of-Tau ceremony
   replaces it, on-chain acceptance is conditional on trusting the setup
   operator. Publishing on-chain removes the need to trust the operator's
   *claim*; it does not remove the need to trust the *ceremony*.
2. **The circuit binds a prover-supplied buffer.** It proves a buffer was
   zeroized, not that the live key was.
3. **Decryption is not encoded in-circuit.** The wiped buffer is not tied to the
   time-locked ciphertext.

What on-chain publication provides unconditionally: immutability, public
timestamps, per-mission replay resistance, and an audit trail nobody can quietly
revise. That is worth having independently of the above.

## Generating deployment arguments

```bash
cargo run -p chronos-snark --release --example export_solidity
```

Prints the `Groth16Verifier` constructor arguments, then a sample proof in
calldata form. The example verifies that proof natively before printing it, so a
failure on-chain isolates to the encoding rather than the proof.

## Deploy

```bash
# 1. Verifier, with the exported constructor arguments
forge create contracts/Groth16Verifier.sol:Groth16Verifier \
  --constructor-args <alpha> <beta> <gamma> <delta> <ic>

# 2. Registry, pointing at the verifier
forge create contracts/ChronosRegistry.sol:ChronosRegistry \
  --constructor-args <VERIFIER_ADDRESS>
```

Smoke-test with the sample proof before wiring in an agent:

```bash
cast call <VERIFIER> \
  "verifyProof(uint256[2],uint256[2][2],uint256[2],uint256[2])" \
  <A> <B> <C> "[<y0>,<wipePattern>]"
# expected: true
```

## Two encoding hazards

`crates/chronos-snark/src/solidity.rs` exists to handle these. They are the
reason a hand-rolled export usually produces a verifier that deploys cleanly and
then rejects every proof.

**Endianness.** arkworks serializes field elements little-endian; the EVM reads
32-byte words big-endian. `verifying_key_bytes()` returns arkworks' encoding and
must *not* be fed to Solidity — use `export_verifying_key` instead.

**Fp2 coordinate order.** An Fp2 element is `c0 + c1·u`, but the pairing
precompile expects `[c1, c0]` — imaginary part first, the reverse of arkworks'
native ordering. Every G2 point is swapped on export.
`test_g2_export_swaps_c0_and_c1` pins this so a refactor cannot silently restore
the native order.

## Public input ABI

The erasure circuit exposes exactly two public inputs, in this order:

1. `y[0]` — first byte of the VDF output
2. `WIPE_PATTERN` — declared post-wipe byte, `0xFF` for the triple-pass wipe

This ordering is fixed in `ErasureCircuit::generate_constraints`, asserted by
`test_public_input_count_and_order`, and hardcoded as
`PUBLIC_INPUT_COUNT` in the verifier. Changing the circuit's public inputs
requires regenerating the key and redeploying.

Unaudited, and not yet deployed or tested against a live EVM. The Solidity has
